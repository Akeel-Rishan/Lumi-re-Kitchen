# Reservation lifecycle

This is an intended contract, not a runtime state machine implementation. Numeric booking defaults are owned by [restaurant policies](restaurant-policies.md). Actors are constrained by the [permission matrix](../security/permission-matrix.md). Customer means a currently authorised reservation-scoped customer, never possession of a booking reference alone.

## Common command requirements

**LIFE-01 — Atomic, audited, idempotent commands.** Check current state, record version, actor permission, policy and an authoritative decision instant after acquiring required locks. Time-sensitive validity is evaluated at that instant, not at HTTP arrival or worker enqueue time. Mutation, allocation changes, safe audit entry, unique event/outbox records and idempotency result commit together. An identical successful command retry returns its original outcome without new transitions, notifications or allocations; the same key with another payload fails. A fresh stale version returns conflict and current permitted review data. GET never mutates domain state. Read-only availability evaluates expired holds logically; allocation commands reconcile them under locks before claiming space.

Audit: actor/service identity, source channel, action, reservation/version, previous/next state, authoritative timestamp, reason where required, allocation changes and correlation/idempotency identifiers (never management tokens). Preserve historical allocation versions, including released portions, separately from active capacity. Terminal means no ordinary outbound transition; create a separately linked replacement through current rules instead of reopening.

**LIFE-02 — Exhaustive ordinary transition set.** “Operational actor” means enabled Staff, Manager or Owner under SEC-02/03; it never implies an invariant bypass. All edges require LIFE-01. No other edges, including terminal reopening or arrived → no_show, are allowed.

**LIFE-08 — Metrics:** declined and expired are separate decision outcomes, never cancellation aliases. Retain separate event types and status counts; cancellation metrics include only actual cancelled transitions, with source state/customer-vs-staff dimensions. Do not count declined/expired or notification failure as cancelled. Denominators, service-date versus creation-date basis, timezone and included statuses must be explicit in Phase 13; a pending-cancellation is not automatically a cancellation of a confirmed booking.

## Hold and time-sensitive rules

**LIFE-03 — Pending hold deadline (authoritative default).** For a new request, approval_deadline = min(request creation instant + 2 elapsed hours, reservation start). Expose it before submission and in receipt/management/staff views. pending consumes capacity only while now < deadline. Background expiry is a durable cleanup/notification mechanism, not a prerequisite for correct availability. A competing booking command must reconcile overdue holds and enforce constraints in its transaction, then retry allocation if needed. Availability may omit expired holds without mutating them; final booking still rechecks.

Approval, editing, cancellation and expiry serialize on the same booking/allocations. An approval waiting on a lock must re-evaluate the clock after acquiring it. Approval that validly wins before deadline prevents subsequent pending-expiry; at/after deadline expiry wins. An overdue stored pending status is displayed as expired/unavailable for approval, with a pending reconciliation indicator only in staff diagnostics. No indefinite hold exists merely because the worker is delayed.

Illustrations derived from policies: a request for Tuesday 19:30 created at 16:00 has deadline 18:00. Created at 18:30 for that same start, it has deadline 19:30. The latter meets online notice exactly, but is already inside the customer-edit cutoff; disclose staff assistance for edits. The two-person lunch at 13:00 occupies [13:00,14:45); a second allocation at 14:45 is mathematically adjacent but not an eligible lunch booking under the initial slot/service rules.

**LIFE-04 — No-show.** Apply TR-09 explicitly; arrived and seated never qualify. A retry cannot generate another notification or release capacity twice. If arrival and no-show race, one wins under state/version control and the other receives a conflict. Corrections to a mistaken no-show require a future separately authorised correction workflow, not reopening a terminal reservation.

**LIFE-05 — Arrival, seating and overruns.** Arrival does not allocate again or extend occupancy. Normal seating retains the reserved end even if late; staff explain the remaining dining time. Early seating or an extension is a distinct allocation adjustment requiring Manager/Owner, reason, snapshot of proposed boundaries, service-closing fit and an atomic capacity check. Staff can request escalation but cannot force the change. If the guest remains beyond expected dining end, alert staff and mark affected next bookings at risk; suppress new availability for that physical resource while the incident is unresolved. Keep all existing future reservations intact. Manager resolves via a checked reassignment, guest-agreed reschedule or authorised cancellation of an affected booking, then retries the adjustment. Never overwrite the next booking or represent physical reality as a second valid allocation.

**LIFE-06 — Completion and cleanup.** Normal completion shortens remaining dining occupancy and replaces the future portion with cleanup [actual completion, actual completion + the booking's snapshotted turnaround). Preserve prior versions and actual timestamps. The union must not overlap another booking/hold/block. If actual completion + buffer is later than the agreed end, Manager/Owner must check the extension atomically; Staff may report the observed completion and request escalation. On conflict, do not partially release capacity or falsely declare cleanup finished: return operational conflict, keep the booking seated and its existing allocation, and record the reported actual completion as an incident observation. Suppress affected resource availability under LIFE-05; Manager resolves the conflict before the command can commit using the original actual-completion timestamp.

Planned extensions must fit service closure. If actual dining/cleanup has already overrun closing, treat it as a recorded policy violation, not a newly permitted booking window: only Manager/Owner may resolve the incident with reason and actual timestamps, check conflicts, and complete with the actual cleanup interval. Future availability remains subject to the original service windows. This factual incident-resolution path uses TR-12, cannot fabricate or backdate a conflict-free interval, and cannot overwrite another allocation; unresolved conflicts still prevent completion commit and require explicit affected-booking resolution. This is not authority to promise an extension past closing. A completed booking's cleanup expires by its interval end without a further reservation transition.

Example: four guests at 18:00 have agreed dining end 20:00 and occupancy end 20:15. Completion at 19:40 yields cleanup until 19:55; the subsequent 20:00 grid start can become available. Completion at 20:20 proposes cleanup until 20:35; if another booking starts 20:30, completion returns conflict and the next booking remains unchanged.

## Atomic edits, distinct from ordinary state transitions

**LIFE-07 — Rescheduling/party changes.** For live pending/confirmed bookings before start, check permission, old version, current policy and capacity, including customer cutoff against both old and proposed start. Lock old/new resources deterministically, reserve new allocation and release old in one transaction. On edit failure keep old time, party, status, deadline, tokens, snapshots and allocations unchanged. Independent natural expiry remains effective: an already-overdue request is not live, cannot be edited, and is reconciled via TR-06 rather than kept pending as an edit rollback. Same-table overlap with the booking's own old version is not a competing reservation; replacement still cannot overlap another booking.

- A confirmed booking with resulting party in the instant range stays confirmed. Any party-size change resulting in the approval range requires renewed approval, including a previously approved party changing size within that range. It becomes pending only after explicit acknowledgement by the actor and an explanation of lost confirmed status. For staff-assisted changes, record guest acknowledgement. Start a new pending episode at accepted edit time; calculate min(episode start + LIFE-03 hold lifetime, proposed start). If no time remains, reject edit; successful result clearly states pending, with a new deadline. A time-only edit to an already approved large party retains confirmed status if every current policy/capacity check succeeds; it is not a new party-size approval request.
- A live pending booking stays pending even when edited into the instant range. Recalculate deadline as min(existing deadline, original pending-episode start + LIFE-03 hold lifetime, proposed start). Editing never refreshes or extends a pending hold; an earlier start can shorten it. At/after its deadline, an edit fails and expiry is reconciled. A later confirmed → pending edit is a new episode with its own audited acknowledgement, not an extension of a currently pending episode.
- A pending edit after staff approval is not replayed as though still pending: use version checks, return conflict and require review.
- Arrived/seated bookings do not use ordinary customer rescheduling. Their only time adjustment is the operational process in LIFE-05. Terminal replacement is a new booking linked for audit and must independently pass current rules.
- Request-text edits preserve timing, allocation, status and deadline. Contact ownership changes are excluded (SELF-06). Time/party edits rotate management credentials under SELF-03. Send an amended confirmed/pending result after commit; do not issue a generic “confirmed” notice for pending.

## Separate entities

**SEP-01 — Waiting list.** Enrollment is a separate entity and consumes no capacity, creates no reservation and promises no booking. An eventual offer owns a distinct time-limited allocation hold with explicit issued_at/expires_at and identity, and expires at equality. Phase 11 must supply a finite configured offer lifetime and queue rules before enabling offers; no fallback indefinite offer is permitted. Acceptance before expiry atomically converts the entire hold to a reservation through shared commands, preserving exclusive table ownership. Apply current party/approval rules: instant-range acceptance confirms; approval-range acceptance creates a pending episode with LIFE-03 deadline. If revalidation fails, no partial reservation is created and the offer retains its original deadline unless explicitly expired/revoked. No offer implementation or queue policy is added in this step.

**SEP-02 — Communications.** Email/WhatsApp queued, sent, delivered, failed and retrying states live on communication records, not reservation.status. Approval, arrival and reminder delivery are independent events; marketing consent is separate permission data. Durable outbox failure after a committed booking does not undo it. Retry/deduplicate delivery and expose operational failure to authorised staff; never instruct a customer to rebook merely because a message failed.
