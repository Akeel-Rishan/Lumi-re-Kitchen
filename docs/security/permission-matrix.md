# Permissions and reservation-scoped access

Intended security contract only; no authentication, sessions, database policies or endpoints are implemented. [Policies](../domain/restaurant-policies.md) own booking defaults and [lifecycle](../domain/reservation-lifecycle.md) owns valid transitions. These permissions never create an otherwise invalid transition or allocation.

## Enforcement rules

| ID     | Requirement                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| ------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| SEC-01 | Deny by default. Enforce on every server command/query and in database access policies. Public clients never receive privileged Supabase credentials. UI visibility is only presentation. Treat customer-supplied role, reservation ID, field masks and table assignment as untrusted.                                                                                                                                                                                                                               |
| SEC-02 | Staff identities must be enabled and checked against current server-side role/revocation state on each privileged request and at mutation admission. A stale UI, cached role claim or refresh token cannot retain access after disablement/demotion. Invalidate sessions and ensure database policy reads current authorisation state.                                                                                                                                                                               |
| SEC-03 | Role inheritance: Manager includes Staff; Owner includes Manager. No role, including Owner or background service, bypasses non-overlap, transaction, pending-deadline, state or mandatory approval rules. After-cutoff assistance uses only OPS-01's explicit waivers, reason and audit, never a generic force flag.                                                                                                                                                                                                 |
| SEC-04 | Background identities are separate per operation: expiry/reconciliation, outbox delivery/reminders, offer expiry and retention. Grant only relevant records/commands, never interactive Owner authority. Automated jobs cannot declare no-show, approve requests, publish content or initiate an unscoped export. Scope a retention job to a specifically approved policy/action.                                                                                                                                    |
| SEC-05 | Sensitive Owner actions require recent reauthentication, purpose/reason and audit. Exports are minimised, time-limited downloads with access logging; role administration cannot remove/disable the last enabled Owner. An Owner cannot grant capabilities outside the product's invariant boundary.                                                                                                                                                                                                                 |
| SEC-06 | Integration credentials are write/rotate/revoke only via restricted server administration; show provider/configuration status, never read back the secret. Secret references belong in server infrastructure, not public content, customer output, exports or audit payloads.                                                                                                                                                                                                                                        |
| SEC-07 | Separate published public projections from drafts, internal notes, guest contacts, policy administration and unpublished assistant knowledge. Public retrieval and assistant indexing can access only approved published information. Enforce record and field scope, not merely page permissions.                                                                                                                                                                                                                   |
| SEC-08 | Staff see operational reservations and the minimum guest name/email/phone and request text needed to run service. Cross-visit customer history and internal longitudinal notes require Manager/Owner. Customer views exclude all staff-only notes, contact details for other guests, audit internals and provider secrets. Retention/deletion must account for necessary audit integrity through redaction/pseudonymisation, with approved retention periods specified before Phase 9/14 production data collection. |

Customer profiles/account-wide history are a later distinct authorisation scope, not implied by Own access.

## Customer self-service contract

| ID      | Requirement                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| SELF-01 | A valid reservation-scoped session may read that reservation and mutate only pending/confirmed while still live and satisfying POL-10. At the exact cutoff allow; below it deny with staff-contact guidance. Read access to terminal results remains until access expiry; arrived/seated/terminal states cannot be customer-edited or cancelled. Time/party changes use LIFE-07; request-text changes use DATA-02.                                                                                                                                                                                                                                                                                                                                                             |
| SELF-02 | A reference, surname, email or phone alone is never authority. Generate at least 256 bits of cryptographically random management-token entropy; store only a cryptographic hash, reservation scope, credential version, issued_at, expires_at and revoked_at. Compare securely, rate-limit verification and return generic unavailable/invalid access responses for invalid, expired, revoked or wrong-reservation credentials. Never distinguish whether an unrelated reservation exists.                                                                                                                                                                                                                                                                                     |
| SELF-03 | Proposed default link expiry is the agreed dining-end instant (excluding turnaround) plus 24 elapsed hours. Valid only while now < expires_at and not revoked. Mutation permissions still depend independently on state/cutoff. Issue on successful booking/request; explicit revocation, suspected compromise and reissue/resend rotate the credential version and revoke older tokens/sessions. A successful time/party edit rotates credentials and derives a new expiry from the new agreed end. Failed edits change nothing. Completion can shorten expiry to actual completion + 24 hours but cannot extend an already-issued credential automatically. Cancellation/decline/expiry leave existing access read-only until its existing expiry unless explicitly revoked. |
| SELF-04 | GET/email previews render an inert generic management landing page; never cancel, edit, approve, consume a hold or redeem a token automatically. Proposed transport: token in URL fragment, extracted by a minimal client component on explicit user action and exchanged in a redacted POST body. Remove the fragment from browser history immediately after reading it; no analytics/third-party resources on that page; Referrer-Policy: no-referrer and no-store responses. Never log URL fragments, exchange bodies, tokens or session cookies. Infrastructure logging/redaction is part of the later integration acceptance gate.                                                                                                                                        |
| SELF-05 | On explicit token exchange, create a cryptographically random opaque session scoped to one reservation, stored hashed server-side, in a Secure, HttpOnly, SameSite cookie. Default absolute lifetime 30 elapsed minutes, bounded by the underlying link expiry. Check token credential version/revocation and current reservation state on every request, including database access. Use explicit POST for mutations with CSRF protection and Origin validation; no mutation on GET. Rotate the session after successful credential rotation; old sessions fail immediately. Link possession does not establish an account-wide identity.                                                                                                                                      |
| SELF-06 | Ordinary self-service cannot change verified contact ownership. Initial contact collection is operational data, not proof of verification. Correcting/replacing email or phone requires a separately verified workflow for the new destination and existing authority, fraud controls, reason/audit and credential rotation; until that workflow is specified and implemented, deny contact-transfer edits and direct to staff assistance. Staff assistance is not permission to overwrite ownership without verification.                                                                                                                                                                                                                                                     |
| SELF-07 | Secure-link resend returns the same acknowledgement and comparable timing for existing/nonexistent records. Proposed defaults: at most 3 attempts per normalised destination per rolling hour and 10 per source IP per rolling hour; count unsuccessful attempts too, use privacy-conscious hashed limiter keys and do not expose which limit/record matched. Send only to the stored destination, never caller-supplied replacement contact. A queued resend revalidates version before delivery and cannot revive revoked/terminal mutation permissions. Apply abuse controls to public booking, token exchange and waitlist entry as well; tune additional limits before exposure.                                                                                          |
| SELF-08 | Booking details follow DATA-01/02. Transactional communication channel preferences and any needed channel permissions are separate from optional, unselected marketing consent. Declining marketing does not prevent booking, confirmation or secure access. Do not treat approval, arrival, reminder delivery, a special request or possession of a phone as marketing consent. Delivery failure follows SEP-02.                                                                                                                                                                                                                                                                                                                                                              |

Successful resends rotate the token at issuance; older queued management links must be superseded rather than delivered as usable credentials. If issuance/delivery fails, never report that access or a reservation mutation succeeded when it did not. A generic resend acknowledgement means only that a valid request will be processed. Before actual integration, define a safe trusted delivery payload mechanism: raw management tokens must not leak into ordinary durable message/audit logs; use a narrowly scoped encrypted delivery secret with short retention, erased after delivery, while the credential store keeps hashes only.
